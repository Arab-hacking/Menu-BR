## 2. Сетевой слой

### 2.1 Формат пакета-синхроструктуры

Диспетчер `NetGame.cpp` (вход функции ≈ `0x1990a78`, ветвления `0x1991000–0x1991c14`,
ассерт-блоки `0x1991e10–0x1992e40`) читает из битового потока RakNet строго по порядку:

```
[u8 packetId]  [u16 syncKey]  [синхро-структура переменной длины]
   │             │
   │             └─ для 30/32/33/34/38/39 = id игрока → GetPlayerById (0x19aada4, максимум 1503)
   └─ ключ switch: 14, 19, 29, 30, 32, 33, 34, 38, 39
```

Ассерты этого диспетчера лежат в `NetGame.cpp` и вскрывают его смысл дословно:

* `Verify failed!` / `Assertion failed!`
* `"Invalid packetId for sync struct: timestamp=%u, id=%u, playerId=%u, packetLen…"` (строка 0x77 = 119)
* `(Traits::syncStructId<TPacket> == packetId)` — шаблонная проверка «пакет принадлежит этому типу»
* `operator()` (из `0x40f2b1`) — тела инстанцирований шаблона

Читатели (десериализаторы) и «применятели» (запись в объекты) — разные функции:

| packetId | Читатель | Применятель | Размер структуры (по читателю) | Кто это |
|---|---|---|---|---|
| **30** `0x1e` | `0x19d053c` | `0x19c9e50` | `u16×3 · 12 Б позиция · кватернион · u16×2 · u8×2 · vec3 скорости` | основной синк игрока |
| **32** `0x20` | `0x19d1414` | `0x19cdba8` | `u16 + u8 + 5×96 бит + u32` = 68 Б | **синк машины (CVehicle)** |
| **33** `0x21` | `0x19d1588` | — (данные кладутся в синхро-кэш; применятеля в диспетчере нет) | ровно `ReadBytes(26)` | связка «игрок ↔ машина» (гипотеза, см. §5) |
| **34** `0x22` | `0x19d0e54` | `0x19cc764` | битовая, поля до `+0x3B` | **InCar sync — игрок за рулём** |
| **38** `0x26` | `0x19d11d0` | `0x19c9d88` → `0x19f72c0` | `ReadBytes(31)` | OnFoot sync (игрок на ногах) |
| **39** `0x27` | `ReadBytes(0x38)` в ветке | `0x19ce310` | 56 Б | **кран/порт (Crane sync)** |
| **29** `0x1d` | `ReadBytes(0x28)` | `0x19cd154` | 40 Б | смежный синк (задевает модуль транспорта, `0x1b8ad88`) |
| 14 `0x0e`, 19 `0x13` | — | — | — | служебные ветки (в живой сессии не встречались) |

### 2.2 id 34 — InCar sync (игрок за рулём) — точный формат

Читатель `0x19d0e54` (вызов из ветки `0x1991970`), порядок чтения — ровно такой:

| Смещ. в структуре | Как читается | Смысл | Куда применяется у игрока |
|---|---|---|---|
| `+0x00` | `ReadBits(16)` | **id машины (сетевой)** | `RemotePlayer+0x150`, `ped+0x54a` |
| `+0x02` | `ReadBits(16)` | u16 (флаги/место) | — |
| `+0x04` | `ReadBits(16)` | u16 | — |
| `+0x06` | `ReadBits(16)` | флаги (проверяется бит 0 бита-0) | — |
| `+0x08` | `0x19d0710` (компресс. чтение) | **кватернион (4×f32)** | `RemotePlayer+0x94` (+0xA4/+0xB4/+0xC4) |
| `+0x18` | `ReadBytes(12)` | **позиция 3×f32** | то же поле позиции |
| `+0x24` | `0x19d095c` (компресс. чтение) | **скорость 3×f32** | проверяется `IsNaN` |
| `+0x30` | `ReadBits(16)` → `ucvtf` | u16 → f32 (здоровье машины?) | — |
| `+0x34` | `ReadBits(16)` | u16 → f32 0…1000 | `RemotePlayer+0x140` |
| `+0x36` | `ReadBits(16)` | u16 → f32 0…1000 | `RemotePlayer+0x144` |
| `+0x38` | `ReadBits(8)` & 0x3F | 6 бит флагов | — |
| `+0x39` | 1 бит | флаг → метод машины | `CVehicle::…` `0x1b7f444(bool)` |
| далее | ещё биты (`0x19d0ff0+`) | хвост структуры | — |

Применятель `0x19cc764` (единственный вызов из `0x19919d4`) и его ассерты в `RemotePlayer.cpp`:

* `"Remote player InCar sync - move speed(%f, %f, %f) isn't valid! player id: %u; vehicle id: %u, in sync: %u"` — строка 0x48a = **1162**, читает f32 по `+0x24/+0x28/+0x2C`;
* `"…quat(%f, %f, %f, %f)…"` — строка 0x491 = **1169**, читает f32 по `+0x0C/+0x10/+0x14/+0x08`;
* `"…pos(%f, %f, %f)…"` — строка 0x49E = **1182**, читает f32 по `+0x18/+0x1C/+0x20`.

Что применятель делает с объектами (это и есть «структура машины» со стороны сети):

```
player+0x94/0xA4/0xB4/0xC4 ← 4 блока по 16 Б из структуры (+0x00/+0x10/+0x20/+0x30)
player+0xD4               ← u16 из структуры+0x40
player+0x140, +0x144      ← u16 из +0x34, +0x36 (через ucvtf)
player+0x150              ← u16 из +0x00  == id машины
player+0x152              ← 0 (сброс «предыдущего»)
player+0x154              ← u32 из дескриптора пакета
player+0x1F8, +0x1FC      ← глобальный тик
player+0x118              ← 0x13 (19) = состояние «в машине» (вызов 0x19ca4d4)
ped+0x54A                 ← u16 id машины
CVehicle+0xB8             ← указатель на RemotePlayer  (двусторонняя связь!)
CVehicle+0x430            ← проверяется на ненулевое
```

Поиск самой машины: `x0 = [0x37809c8]` (пул машин) → `0x19d2fdc(id)`; если машина найдена,
ей прописывается занявший `[CVehicle+0xB8] = RemotePlayer*`, иначе занявший сбрасывается в 0.

### 2.3 id 32 — Vehicle sync (состояние самой машины)

Читатель `0x19d1414` (вызов из ветки `0x19918a0`):

```
+0x00 ReadBits(16)   — id машины (u16)
+0x02 ReadBits(8)    — u8 (флаги)
+0x04 ReadBits(96)   ⎫
+0x10 ReadBits(96)   ⎪
+0x1C ReadBits(96)   ⎬ 5 блоков по 12 байт: позиция, поворот, скорость, …
+0x28 ReadBits(96)   ⎪
+0x34 ReadBits(96)   ⎭
+0x40 ReadBits(32)   — u32 (время/маска)
итого 68 байт структуры → на проводе ≈ 71 байт с заголовком
```

Применятель `0x19cdba8` (единственный вызов из `0x1991904`) не пишет в `CVehicle` напрямую,
а ведёт **кэш синхронизации машин** у сетевого менеджера:

* поиск: `ldrh w1,[struct] → `GetByNetId` (`0x19d2fdc`, глобал `0x37809c8`); если машины нет —
  узлы с этим id **вычищаются из хэш-таблицы** (unlink + `free`), т. е. это поток «машина появилась/исчезла»;
* хэш-таблица: `менеджер+0x210` (объект), `+0x218` — корзины, `+0x220` — число корзин, `+0x228` — счётчик;
  узел **0x50 байт**: `+0x00` u16 ключ (id машины), `+0x04` тик, `+0x08` флаг активности,
  `+0x0C…+0x4C` — данные синхроструктуры, `+0x50` — указатель на следующий узел;
* обновление узла: `+0x0C ← struct[0..16)`, `+0x1C ← +0x10`, `+0x2C ← +0x20`, `+0x3C ← +0x30`, `+0x4C ← +0x40`.

Побочно: вспомогательный `0x19d00b4` (вызов только отсюда) и `0x19cdd1c` (вызывается из `0x10dfdf0`) работают
с тем же кэшем; `0x19cc5ac` — потребитель (2 вызова: `0x19aeecc`, `0x19cdec8`).

### 2.4 id 39 — Crane sync (кран/порт)

* 56-байтная фиксированная структура (`ReadBytes(0x38)`), применятель `0x19ce310`.
* Ассерт: `"Crane sync received for vehicle with wrong type"` (`RemotePlayer.cpp`, `0x19ce414`) +
  условие `vehicle->IsPortCrane()` (строка `0x42e180`).
* Рядом живёт `SetCraneRopeLength` — `NetVehicle.cpp`, функция `0x199f320` (вызов из `0x199f3a4`),
  т. е. длина троса крана приходит/применяется в сетевом слое машин, а не в RPC.

Сопоставление с каналом RPC (по `session_rpc_flow.json`):

* RPC 419 `RemotePlayerSpawnedEvent` дал ровно пятерых: **258, 279, 382, 405, 463** (скины 182, 281, 288, 6858, 5500034);
* RPC 325 `RemotePlayerUnspawnedEvent` — те же пятеро;
* значит заголовок `u16` у 34/33 = **id игрока**, и наблюдение «382/258/279 только в 34, а 463/405 только в 33» —
  это разные категории синхронизации для разных игроков (за рулём / в машине-иначе), а не разные сущности;
* id машины виден **внутри структуры 34**: у игрока 382 — машина **48**, у 258 — **207**, у 279 — **58**.

### 2.6 id 33 — структура и гипотеза

Разбор реального пакета (заголовок 3 Б + структура 26 Б):

```
21 cf01 | 3000 0100 4c00 64000000 00000000 0183f844 73d60cc5 e0e93e41
│  │       │    │    │    │        │        │        │        └─ f32 z = 11.91
│  │       │    │    │    │        │        │        └────────── f32 y = -2253.4
│  │       │    │    │    │        │        └─────────────────── f32 x = 1989.09
│  │       │    │    │    │        └──────────────────────────── u32 0
│  │       │    │    │    └───────────────────────────────────── u32 100
│  │       │    │    └────────────────────────────────────────── u16 76

```

Частота ~2.3 Гц (интервалы 45–100 мс), только S2C, размер неизменный. Позиция едет
(1988 → 2064 по x за сессию), значения 100/0 стабильны → похоже на «здоровье 100 / броня 0».
Первый u16 структуры (48) совпадает с id машины игрока 382 из пакета 34 — то есть это, скорее всего,
**тоже ссылка на машину**, а не на игрока. Вывод-гипотеза: **id 33 = «игрок находится в машине X,
место Y, состояние Z, позиция»** — «тихий» канал для тех, кто уже в машине (применяется из кэша,
а не в момент прихода пакета). Семантика полей 1/76 окончательно не доказана — см. §6.

## 3. Нативный слой

### 3.1 Пул машин (VehiclePool)

| Что | Адрес/значение | Доказательство |
|---|---|---|
| Глобал пула | **`0x37809c8`** (рядом: менеджер игроков `0x37809c0`, таблица цветов `0x3780c74`) | `adrp x8,#0x3780000; ldr x0,[x8,#0x9c8]` в применятелях 32/34 и в деструкторе машины |
| Ёмкость | **2000 слотов** (`cmp x8,#0x7d0`) | цикл поиска `0x19d38d4` |
| Элемент | 8 Б: `obj = pool[i]`, у обёртки `[obj+0x00]` = **сетевой id** | `ldr x9,[x0,x8,lsl #3]; ldr x9,[x9]; cmp x9,x1` |
| Поиск по сетевому id | **`0x19d2fdc`** (`GetByNetId(u16)`, 28 мест вызова) | вызовы из применятелей 32/34 и из геймплейного кода |
| Снятие с пула | `0x19d38d4` — ассерт `VehiclePool.cpp` стр. **0x101 = 257**, тексты `Invalid vehicle`, `!m_vehicles[i] \|\| m_vehicles[i]->GetVehicle() != vehicle` | сайты `0x19d392c…0x19d394c` |
| Кто вызывает снятие | деструктор/удаление машины `0x1b78630` (в регионе `Vehicle.cpp`) — передаёт и пул, и саму машину | `0x1b7861c: adrp…+0x9c8; ldr x0,[x8]; mov x1,x19; bl 0x19d38d4` |

## 6. Что НЕ доказано и где границы анализа

1. **Момент появления машины в кадре не записан.** Ни один пакет в сессии не содержит пары
   «id модели 400…611 + координаты+цвета»; типы **32** и **39** отсутствуют вовсе. Значит спавн/деспавн
   машины произошёл вне окна записи (мир был уже загружен), и точный формат «VehicleSpawned» по этой
   сессии не проверить. Кандидат на роль спавна — применятель 32 (он умеет и создавать запись в кэше,
   и удалять её) и/или RPC, которого в таблице `rpc_table_final.csv` нет (там 125 записей, транспортных имён — 0).
2. **Семантика полей 33** (`1`, `76`, `100`, `0`) и то, кто именно «в машине» — из кода не читается
   (применятеля в диспетчере нет, данные кладутся в кэш). Доказано только: заголовок = id игрока,
   первый u16 структуры совпадает с id машины из типа 34, частота ~2.3 Гц, размер фиксирован.
3. **`278` в C2S-заголовках типа 34** не отождествлён: в списке спавнов RPC 419 его нет,
   но ник для него в RPC 384 есть; локальный игрок по RPC 345/364 = **411** (`Arab_Kalashnikov`).
   Наиболее вероятно: 278 — id, под которым клиент видит свой транспорт в канале 34 (проверяется
   только новой записью трафика «сел в машину / вышел»).
4. **Офсеты CVehicle за пределами известных** (+0xB8, +0x430, moveSpeed-указатель) не размечены:
   для полного «дамп-листа» нужен либо живой дамп памяти процесса, либо разбор конструктора `CVehicle`
   (регион `0x1b7cxxx`), что упирается во время дизассемблирования, а не в доступ к данным.
5. **RPC-таблица не содержит транспортных имён** — это не пробел таблицы, а факт: RPC 323, у которого
   ранее предполагалась связь с транспортом, на деле строит JSON-аналитику/UI (`{"t":7,"b":[…]}`, кнопки HUD).

## Дополнение: сверка Vehicle Structure с 16.110.18323 (21.10.2026)

Основной текст выше описывает 16.106.17587. Для сравнения использована `libblackrussia-client.so` из APK CDN-коммита `34822_674ac225_1791889252039` (SHA-256 `70467b632788d03753dd8de625561d69461b81c72e4877796e2e006192fc731d`). VA — адреса внутри ELF; они не учитывают ASLR.

### Подтверждённые адреса новой сборки

| Объект/функция | 16.106.17587 | 16.110.18323 | GOT 16.110.18323 |
|---|---:|---:|---:|
| `VehiclePool*` | `0x37809C8` | **`0x37FBEC8`** | `0x2412840` |
| `VehiclePool::GetByNetId` | `0x19D2FDC` | **`0x1A1C1C8`** | — |

Глобал и GOT подтверждены через релокации и обращения к коду новой `.so`; `GetByNetId` сопоставлен по совпадающему телу lookup.

### Повторно проверенные свойства структуры

- `GetByNetId` в новой библиотеке проверяет верхнюю границу `0x7CF` (ID до 1999 включительно), индексирует пул по `id*8` и загружает указатель объекта из слота. Значит, подтверждаются **2000 слотов по 8 байт**.
- В коде текущего InCar sync повторно встречаются `CVehicle+0xB8` (указатель связи с RemotePlayer) и чтение поля класса по `CVehicle+0x430`.
- Там же видны обращения к `+0x540` и `+0x548` у связанного объекта игрока и координатам педа по `+0x38/+0x40`.

Итого: **абсолютные VA пула и `GetByNetId` изменились; размер и индексирование vehicle pool, а также перечисленные поля, проверенные в коде новой сборки, остались прежними.** Поля производных классов и размеры всех vehicle-подклассов из RTTI старой версии в рамках этой сверки заново не измерялись.

VA диспетчера `NetGame.cpp` и reader/apply для sync 32/34/прочих пакетов пока не сопоставлены с новыми функциями. Старые VA из таблиц выше нельзя переносить в 16.110.18323; нельзя также получать новые VA простым прибавлением сдвига `.text`.

Подробная таблица сопоставлений и методика: `PLAYER_VEHICLE_COMPARE_16.106_16.110.md`.
