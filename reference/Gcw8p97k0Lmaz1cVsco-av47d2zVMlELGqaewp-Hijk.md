Дополнение к `VEHICLE_STRUCTURE.md`: там — сети и пул, здесь — **классы, размеры, конструкторы и офсеты полей**.
Файл `.so` — `br_analysis/live/libblackrussia-client.so` (38 238 624 Б).

---

## 0. Метод (почему это не догадки)

`.so` **очищен**: таблицы символов (`.symtab`/`.strtab`) нет, `nm` даёт «no symbols». Имена восстановлены так:

1. читаем `.rela.dyn` (141 392 записи: 132 665 `R_AARCH64_RELATIVE`, 8 341 `ABS64`, 386 `GLOB_DAT`);
   `.rela.dyn` **не сжат и не удалён** — в нём лежат реальные адреса функций, которых нет в файле;
2. ищем релокации, чей addend указывает на строку вида `8CVehicle` / `11CAutomobile` → это `typeinfo+8`;
3. `typeinfo` = этот адрес − 8; `vtable` = адрес, куда указывает `vtable[-1]` ⇒ **4 412 имён типов, 11 632 втейбла**;
4. методы класса = подряд идущие релокации, указывающие в `.text` (`0xfb01a0…0x227a410`);
5. конструктор = код, который кладёт адрес втейбла в `[this]` (`adrp`+`add` ⇒ `str x8,[x0]`);
6. дамп конструктора: `str/strb/strh/stp` с разрешением констант (`mov/movk/movn/fmov/movi`, `adrp+add`, `adrp+ldr`) и смещений от базового регистра.

⚠️ Секции сдвинуты: `va2off = 0x4000` (`.data.rel.ro` va `0x22878c0` ↔ off `0x22838c0`). Для `.text`/`.rodata` смещения нет (LOAD[0] off=0 va=0).

Скрипт-повторитель: **`br_analysis/scripts/50_vehicle_dump.py`** (полный проход ~2 с).

## 2. Фабрика машин — `0x1b815a0` (= `CreateVehicle(modelIndex)`)

Читает информацию о модели (`bl 0x105d734`), берёт **класс из `modelInfo+0x5c`** и создаёт объект нужного размера:

| класс (`+0x5c`) | имя в парсере типов | размер | создаётся |
|---|---|---|---|
| 0 | `car` | `0x1530` | CAutomobile `0x1b3d148` |
| 1 | `boat` | `0x9a0` | CBoat `0x1b5e140` |
| 2 | `train` | — | **не создаётся** (поездов в BR нет) |
| 3 | `heli` | `0x818` | CHeli `0x1b71ae8` |
| 4 | `plane` | — | **не создаётся** |
| 5 | `bike` | `0xa28` | CBike `0x1b53ae8` |
| 6 | `mtruck` | `0x1548` | CMonsterTruck `0x1b73f90` |
| 7 | `trailer` | `0x15a0` | CTrailer `0x1b74be4` |
| 8 | `quad` | `0x1568` | CQuadBike `0x1b74048` |
| 9 | `bmx` | — | не создаётся отдельно (сводится к bike) |
| 10 | `trike` | `0xa28` | CTrike `0x1b76d00` |
| 11 | `prtcrn` | `0x830` | CCrane `0x1b6d58c` |
| 12 | `craneof` | `0x830` | CCrane `0x1b6d58c` |

Вся фабрика — 20 инструкций: `cmp w8,#…` по классу → `mov w0,#размер` → `bl 0x1b77988`(оператор new) → `bl <ctor>`.

### Парсер текстового типа — `0x108517c`
Вызывается из парсера данных (объект с полями `+0x74`, `+0x210`, `+0x5c`), сравнивает строку и ставит класс:

```
'car'→0   'boat'→1   'train'→2   'heli'→0 (!)   'plane'→4
'bike'→5  'trike'→10 'mtruck'→6  'trailer'→7    'quad'→8
'bmx'→9   'prtcrn'→11  'craneof'→12
```
Наблюдаемая странность: ветка `heli` пишет класс **0** (car) и два float'а `(1.0, 1.0)` в `+0x60`; при этом собственный конструктор CHeli пишет в класс 3. Т.е. либо это ошибка/override в данных, либо «heli» помечается флагом, а не классом. Оставлено как есть.

### 4.3 `CBike` (`0x1b53ae8`)
`+0x08 = 100000.0f`, `+0x40 = 4` (байт), `+0x58` = указатель, `+0x1CC = 180.0f`, `+0x1DC = 180.0f` (разворот руля/наклон), `+0x430 = 5`, `+0x9A8 = 5` (байт), `+0x9AC = 1.0f`.

### 4.4 `CBoat` (`0x1b5e140`)
`+0x20 = -0.6283f`, `+0x1D8 = 0.1f`, `+0x1DC = 0.5f`, `+0x7C8 = 7.0f`, `+0x7CC = -10000.0f`, `+0x814 = 7.0f` (два «семёрочных» параметра — вероятно, точка опоры/осадка).

### 4.5 `CHeli` (`0x1b71ae8`)
`+0x78 = 64` (байт), `+0x430 = 3`, `+0x808 = -50.0f`, `+0x814 = 1`.

### 4.6 `CTrailer` (`0x1b74be4`)
`+0x78 = 32` (байт), `+0x430 = 7`, **`+0x1594 = -1000.0f`** — читается в функции `0x1b74d4c` перед ассертом по `m_vecMoveSpeed` (порог «прицеп отцепился/подцепился»).

### 4.7 `CQuadBike` / `CMonsterTruck`
`+0x430 = 8` / `6`; прочих уникальных констант в конструкторах нет (наследуют CAutomobile).

Конструктор прогревает и «рабочие» области, которые наследуют все автомобили:

```

+0x944, +0x948, +0x950        — сопутствующие поля

+0x9D4, +0x9D8                — указатели
+0x9E0…+0x9F4                 — 6 × -0.15f (пороги по колёсам)
+0xA00, +0xA10, +0xA20, +0xA30, +0xA40, +0xA50 — 6 блоков (по колесу)
+0xA74, +0xA76, +0xA78, +0xA80, +0xA8C
+0xB40, +0xB48, +0xB50, +0xB58, +0xB60, +0xB6C
+0xC40, +0xD18, +0xDF0, +0xEC8, +0xFA0 — байтовые флаги (шаг 0xD8 = 216 Б — похоже на массив по колёсам)
```

Шаг `0xD8` между `+0xC40/+0xD18/+0xDF0/+0xEC8/+0xFA0` — сильный признак массива «по колесу» (5–6 элементов), что согласуется с `m_atomics` модели.

## 7. Границы доказанного

* **Доказано кодом**: список классов, втейблы, число методов, адреса конструкторов, размеры объектов (из фабрики), класс-энум `+0x430`, все значения-константы конструкторов (§4), назначение `+0x5C/+0x74/+0x75/+0x230/+0x260/+0x270` у `CVehicleModelInfo`.
* **Не доказано**: имена полей для большинства офсетов CVehicle (можно присвоить только по признакам: «флаг», «порог», «указатель на подсистему»); семантика «горячих» офсетов; что именно в 22 блоках нулей `+0x590…+0x6E0`.
* **Не поймано в сети**: спавн машины (типы 32/39 не встречались); соответствие id модели 400…611 конкретному классу — проверяется по `modelInfo+0x5C` уже из данных, а не из трафика.
* Размер `CVehicle` как такового неизвестен: фабрика всегда создаёт конкретный наследник, поэтому «чистый» CVehicle не аллоцируется.
